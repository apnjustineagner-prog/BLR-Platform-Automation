Onboarding & Processor Credential — Failure Report

QA Automation findings for Dev review
Environment: test-web-admin.billeroo.com (Test) Areas: Onboarding (merchant create), Processor Credential Account: Admin (Super Admin) Observed: 2026-09-16 / 2026-09-17 Severity: High (blocking suite)

Summary

Two distinct failure signatures are blocking the Onboarding and Processor Credential suites:
  • (1) Created merchant not queryable in time — after a merchant is created, it does not appear in the Onboarding table even after 8 reload + search cycles (~60s+). The record IS created, it just surfaces later than the test can reasonably wait. backend slowness
  • (2) Navigation hangs on “Loading…” / never settles — navigating to Onboarding waits on networkidle, but the SPA polls continuously so the network never goes idle → a hard 45s timeout. wait strategy (partly test-side, partly slow nav)
Signature (1) is the same root cause already reported for Payment Console (records not queryable right after write). Signature (2) we have started mitigating test-side, but the underlying navigation is also slow.

domcontentloaded and load both fire — only networkidle never does, because the dashboard/SPA polls in the background continuously.

Impact

  • Automation: Onboarding and Processor Credential smoke/regression suites fail at the create-then-read and navigate steps; the run hits maxFailures and stops early, blocking downstream tests.
  • Potential real users: if a newly created merchant is not immediately queryable, users may not see the record right after saving and could re-submit.

What we’ve done test-side vs. what needs Dev

Test-side mitigations already applied:
  • Reload + re-search up to 8 times after creation (still insufficient on slow moments).
  • Replaced networkidle waits on the Onboarding navigation with a concrete element wait (the merchant “Search:” box) so navigation no longer hard-hangs.
What we need from Dev:
  1. After a merchant/credential is created, how long until it is queryable in the Onboarding list? Is there a write→read replication lag, cache, or async index on the test env?
  2. Is the continuous background polling expected? It prevents the network from ever going idle and slows perceived navigation.
  3. Is this test-infra slowness or app behavior that would also affect production?
  4. Expected SLA for “create → visible in list” so we can size the automation wait correctly.
Note: Signature (1) matches the previously reported Payment Console issue (records not queryable immediately after write) — likely the same backend cause. Signature (2) is partly a test wait-strategy issue (now being fixed) but is amplified by slow navigation on the shared test environment.
