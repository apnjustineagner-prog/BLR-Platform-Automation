Payment Console — Slow / Hanging Response After Confirm

QA Automation findings for Dev review
Environment: test-web-admin.billeroo.com (Test) Area: Payment Console → Confirm → Receipt Processors: ECPay & Bayad Observed: 2026-09-16 Severity: High (flaky)

The problem in one line

After clicking Confirm, the app intermittently sticks on a disabled “Loading…” spinner and does not render the Transaction Receipt for 30–75+ seconds (sometimes never in a single attempt). The identical payment succeeds on retry, so the data is valid — the delay is in the backend response after Confirm.

We raised the automation wait from 30s → 75s to absorb the slowness; even 75s is occasionally not enough, which is why this is a backend concern, not just a test-timeout tweak.

Evidence — DOM captured at the hang

At timeout, the submit control is stuck loading — no receipt, no error, no redirect:

button "Loading..." [disabled]
  - status
  - text: Loading...

Distinct from a real rejection: when an account is genuinely rejected the app redirects to /payment-console-status-error?statusCode=ER.00.05. The hang has no error and no redirect — the request is simply still pending.

Impact

  • Automation: e2e Payment Console tests flake — the receipt gates every later step (Transaction List, View Transaction modal, email receipt). Mitigated with 75s waits + retries, which slows the suite and masks the issue.
  • Potential real users: if Confirm routinely takes this long, users may think the payment stalled, retry, and risk duplicate submissions.

What we need from Dev

  1. How long does the payment-processing call after Confirm (ECPay/Bayad submission) take on the test env? Any known slow dependency (processor round-trip, DB, queue)?
  2. Is there a case where the request never resolves and the spinner stays indefinitely? If so, the UI should time out and show an error rather than spin forever.
  3. Is this test-infra slowness (under-provisioned servers / throttled processor sandbox) or an app-level issue that would also hit production?
  4. What is the expected SLA for Confirm → receipt so we can set a correct automation timeout?
Note on framing: This is framed as slow backend response, not client internet. The consistent “Loading…” spinner + success-on-retry with identical data points to the server taking long to respond rather than a connectivity drop. Client-side network hasn’t been formally ruled out — confirming the server-side timing above would settle it.
